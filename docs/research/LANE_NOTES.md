THE CSP FINDING THAT CHANGES RECOMMENDATIONS. The actual policy in src-tauri/tauri.conf.json is `default-src 'self'; img-src 'self' asset: http://asset.localhost https://asset.localhost https://i.ytimg.com https://*.ytimg.com; media-src …; frame-src …youtube-nocookie…; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'`. Two consequences worth propagating to whoever implements any of this. First, there is NO `data:` in img-src, and CSS background-image / mask-image are governed by img-src — so the canonical internet-standard grainy-gradient recipe (`url("data:image/svg+xml,…feTurbulence…")`) is silently blocked in this app. Every noise/texture tutorial you will find uses it. It must be a real bundled file. Second, there is no worker-src and no child-src, so both Worker and Worklet module loading fall back through to `default-src 'self'` — a Vite-emitted same-origin file passes with NO security-config change, but a blob: URL (the other pattern every tutorial uses) does not. So candidates 1 and 5 are both CSP-clean as long as they are implemented with `new URL(…, import.meta.url)`.

WHERE THE APP IS ALREADY AT OR AHEAD OF THE STATE OF THE ART — this is the most important finding and I want it stated before the list is read as a to-do. (a) The transform-only aurora is not a compromise, it is the correct answer, and the app is genuinely AHEAD of the mainstream here. The technique currently being written up everywhere for 2026 is @property-registered custom properties animated inside gradient definitions. That forces a full repaint of the affected element every single frame on the main thread — the sources are consistent on this. The app's counter-drifting transform fields do the same visual job on the compositor. Do not "modernise" the aurora to @property; that would be a regression dressed as an upgrade. (b) The tiered canvas field is at parity with the current best copy-paste implementations: shadcn.io's "Silk", one of the most-copied 2026 background components, is described as a 192x108 offscreen canvas driven by three phase-offset sine waves and mapped through a five-stop palette — the app's 320x200-upscaled, 30fps-capped, token-coloured field is the same design, at slightly higher resolution. There is nothing to buy here. (c) The tier system itself — min(themeDefault, capability, userPreference), reduced-motion forcing tier 0 globally, pause on window blur, pause on video playback, mushaf route clamped to tier <= 1 — is better engineered than every gallery component I found. None of them pause on blur. That is the difference between a website background and a desktop app background, and it is already done. (d) Choosing no WebGL is now the trend, not a limitation: the 2026 design-trend consensus is explicitly that CSS noise texture and film grain have displaced heavy 3D for conveying depth, to avoid the processor cost. The app arrived at the fashionable answer for principled reasons.

WHERE IT IS ACTUALLY BEHIND, ranked. 1: no texture layer of any kind — this is the single biggest aesthetic gap versus 2026, and it is the cheapest to close, and it works at tier 0 where reduced-motion/Performance-Mode/mushaf users live and currently see a bare gradient. 2: the canvas is on the main thread, so "zero contribution to input latency" is currently a design intention rather than a structural guarantee. 3: every gradient interpolates in sRGB. 4: no perspective anywhere, so there is layered motion but no actual depth. 5: hand-built rim/mask constructs that the platform now does natively.

THINGS THE BRIEF ASKED ABOUT THAT ARE DEAD ENDS, so nobody re-litigates them. `element()` — web-features records support in NO browser; it was a Firefox-only function and Chromium never shipped it. Do not plan around it. CSS `random()` — despite the 2026 write-ups, web-features records it shipped in Safari 26.2 ONLY, with no Chrome/Edge version at all, so it is unavailable in WebView2 today; the staggering/variation use cases it is pitched for still need sibling-index() or JS. `linear-blur()` for native progressive blur is a CSSWG proposal (csswg-drafts issue #13285, opened Jan 2026), not shipped anywhere.

CHROMIUM-ONLY FEATURES I DID NOT GIVE FULL SLOTS, but which are usable here precisely because WebView2 is Chromium and worth a look when touching the theme layer: @function (Chrome 139) would let the 10 themes' ambient parameters be expressed as CSS functions instead of per-theme classes, which is the purest possible expression of constraint 4; if() (Chrome 137) for one-off conditional token values; sibling-index()/sibling-count() (Chrome 138) to stagger layered ambient elements without inline styles; progress() (Chrome 138); corner-shape (Chrome 139) and border-shape (Chrome 147) for surface polish; dynamic-range-limit (Chrome 136), which is genuinely relevant to a glow-heavy dark UI on Windows HDR displays where an accent rim can blow out — currently nothing constrains that. Chrome 150 is the current stable (July 2026); Chrome moved to a two-week release cadence in 2026, so pin your WebView2 floor deliberately rather than assuming latest.

OTHER PACKAGES CHECKED AND REJECTED WITHOUT A SLOT, with registry-verified facts. tsparticles 4.3.2 (2026-07-10, 1.07MB unpacked; @tsparticles/slim 900KB) — the app's ~40-line field already does this and does it better, since tsparticles has no equivalent of the pause-on-video or tier discipline; strictly worse. vanta 0.5.24 — last published 2022-09-16, 1.4MB, three.js-based, and its own documented preset list includes BIRDS, i.e. constraint 1 is violated by the library's public API surface; hard reject. granim 2.0.0 — last published 2018-11-11; abandoned. ogl 1.0.11 (2025-01-27, 423KB) and three 0.185.1 (23MB) — same WebGL-context failure as Paper Shaders, and ogl is the engine under the already-rejected React Bits. gsap 3.15.0 — 6.3MB unpacked and a non-MIT "Standard no-charge" licence; the app already has framer-motion for the only thing it needs springs for. motion 12.42.2 (2026-06-30) is the current framer-motion line and now depends on framer-motion itself; if you ever want the WAAPI-backed off-main-thread `animate()` it is a drop-in, but it is orthogonal to backgrounds and I did not count it as a candidate.

METHOD. I did not trust listicles or bundlephobia. I built the SAME chart six ways as real Vite/esbuild production bundles against one identical React baseline (raw=190,384 / gzip=59,056) and measured with gzip -9. All deltas below are that baseline subtracted. I also drove the app's exact recharts config in the project's own Chromium (/opt/pw-browsers/chromium-1194) to inspect the rendered DOM and pixel-diff it. The repo is untouched — I built scratch apps inside the project only long enough to resolve node_modules, then deleted them; `git status --porcelain` is empty.

MEASURED COST FOR ONE 28-POINT AREA CHART (raw / gzip delta):
  hand-rolled SVG    +2,575 B    / +1,201 B
  d3-shape+d3-scale  +25,632 B   / +9,564 B
  visx               +38,604 B   / +13,885 B
  uPlot              +52,328 B   / +22,031 B (+708 B CSS)
  Observable Plot    +272,525 B  / +89,470 B
  recharts 3.10      +354,039 B  / +100,881 B

HEADLINE: recharts accounts for essentially the ENTIRE 524→898 KB regression (my isolated +354 KB raw vs the observed +374 KB). It is 84x the gzip of a hand-rolled equivalent, to draw 28 points on a chart WITH BOTH AXES HIDDEN. recharts 3's size is structural, not incidental: it rewrote its internals onto Redux, and its hard deps are @reduxjs/toolkit, react-redux, immer, reselect, es-toolkit, victory-vendor, decimal.js-light, eventemitter3, use-sync-external-store, tiny-invariant. Adopting it was the wrong call for this specific chart. That is a judgement about fit, not about recharts' quality — it is a good library for dashboards with many chart types.

BUG FOUND (independent of the size argument). Rendering the app's exact config in Chromium shows recharts propagates the `filter` prop to BOTH child paths: `.recharts-area-area` (the gradient fill) AND `.recharts-area-curve` (the stroke). The fill is therefore blurred and feMerge'd with itself. The comment in StudyCharts.tsx ("the line drawn twice, once blurred underneath") does not describe what renders. Pixel-diffing filter-on-both against filter-on-stroke-only changed 51.66% of pixels with a max channel delta of 85/255 — the fill is materially denser than its declared 0.34 stop opacity and bleeds below the baseline, since the filter region is y=-40% height=200%. Worth fixing regardless of which option is chosen.

CURVE EQUIVALENCE — the load-bearing claim, and I got it wrong first. My initial hand-rolled generator used Fritsch-Carlson tangents and DIFFERED from recharts visibly (max deviation 6.09 user units). d3's curveMonotoneX actually uses a Steffen-style tangent, (sign(s0)+sign(s1))*min(|s0|,|s1|,0.5|p|), with slope2 one-sided endpoints. After porting that faithfully, output is bit-identical to d3-shape across 7 shapes — realistic 28-day data, all-zeros (the empty-library state), monotone ramp, alternating spikes, plateau, single-point-early, single-point-late, and 2-point — once matched to d3-path's default 3-decimal rounding. So "drop recharts, the curve is unchanged" is verified, not asserted. It is ~25 lines and unit-testable against d3-shape in CI if you want a permanent guard.

ON GLOW, GRADIENTS AND AXES — the honest answer is that THIS APP IS ALREADY AT THE STATE OF THE ART, and that is the most useful finding in this lane. A vertical linearGradient fading to transparent, plus a duplicated blurred stroke for glow, IS what the best dataviz on the web does. Both are plain SVG <defs>. No library sells a better glow or gradient, because there is nothing to sell — recharts is not providing either of them here; the app hand-wrote both. Two genuine, library-free improvements exist: feDropShadow collapses the glow to one primitive AND decouples glow colour from the source graphic (verified: flood-color accepts rgb(var(--token)) and resolves to the live theme colour), which is also the clean fix for the double-filter bug; and a marked, labelled final value on the curve is the one sparkline convention the chart is missing.

WHERE SOURCES DISAGREE / WERE WRONG. (1) uPlot's famous "12 KB gzip" did not hold in a React bundle — I measured 22 KB plus CSS, larger than visx. (2) Several 2026 "best React chart library" posts recommend `chart.ts` as a sub-15 KB Tailwind-native library; the npm package is a 433-byte empty stub from 2019 by an unrelated maintainer, and chartts.com is SEO spam. Same failure mode as the already-rejected Bklit. (3) One comparison claimed recharts has "the smallest gzipped bundle at 136 KB" versus visx at 271 KB — my measurements invert this decisively for any single-chart use, because visx is modular and recharts is not. Treat published bundle tables as marketing; measure the chart you are actually shipping.

RECOMMENDATION IF ONLY ONE THING CHANGES: hand-roll the SVG (candidate 1), reclaiming ~101 KB gzip and fixing the filter bug in the same edit. If the team wants a maintained interpolator, d3-shape+d3-scale is the sane middle at ~9.5 KB gzip. Keep the CSS-grid heatmap exactly as it is — and note it is the half of this feature that was built without a library, and also the half with no bundle cost and no rendering bug.
